## Improvements

- **Database name in the project settings.** Next to the database server there's a *Database name* field, filled in from the project's `.env` / `wp-config.php` or its folder name. Changing the server or the name creates that database on save (the server is started if needed) and updates `.env` / `wp-config.php`.
- **Importing a project sets up its database.** Choose the server and name when importing (or *None*); the database is created if it doesn't exist.
- **New projects get a database by default** on the default server; an empty project starts without one.
- **"Default" instead of "none".** PHP, Node.js and Python choices show the version they fall back to, e.g. *Default — PHP 8.4* or *Default — Node.js 22.23.3*, in the project settings, the wizard and the import. Projects set to "none" in 1.0.0-beta.4 go back to the defaults.
- **Saving project settings is confirmed** with a message (or the error).
- **Clearer project settings layout:** path, then domain and document root, PHP and Node.js, database server and name, Python.

## Fixes

- **WordPress with `wp-config.php` in `public_html`** follows database port changes; before, only a `wp-config.php` in the project folder was updated.
- **Database passwords with special characters** (`$&`, quotes, backslashes, spaces, `#`) are written correctly to `.env`, `wp-config.php` and the MySQL client config; before, some of them were garbled.
- **A document root outside the project** (e.g. `C:\` typed by hand) is rejected; before, it could freeze lokaldev.
- **Changing the MySQL/MariaDB login** no longer fails half-way when the server has several accounts for the user; the new login is checked before lokaldev starts using it.
- **A failed database or login change can be retried.** If creating the database or switching the login fails, the previous setting is kept, so saving the same change again tries it again instead of reporting success.
- **Importing a dump that prints a lot** (e.g. contains `SELECT`s) no longer hangs lokaldev, and a broken `.gz` file stops the import with an error.
- **Binary updates are safer.** The new version is downloaded and unpacked next to the installed one, and services are stopped only for the final swap. An update interrupted by a crash or power loss is undone on the next start; before, a database server could come back as a different, empty instance.
- **Cleanup after a crash only stops lokaldev's own processes.** Leftover processes are matched by program and start time, so an unrelated process that got the same ID is never closed.
- **Moving the databases folder is all-or-nothing.** If moving fails part-way, everything goes back to the old folder; a new folder that already holds a database folder of the same name is reported instead of being used silently. When moving to another drive, the originals are removed only after the switch.
- **App updates never touch `data`, `www` or `databases`**, and a failed update removes the files it added before the previous version is put back. What went wrong is written to `update.log`; files that couldn't be restored are kept in `data\update-backup-…`.
